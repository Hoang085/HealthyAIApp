3.1. Triết lý: feed xoay vòng, không phải thẻ cảnh báo cố định

Trước đây mỗi điều kiện sinh ra một thẻ cảnh báo cố định. Vì điều kiện còn đúng thì thẻ vẫn còn, người dùng chưa xử lý xong sẽ thấy mãi cùng một gợi ý — cảm giác bị ép buộc.

Engine hiện tại không dựng thẻ cảnh báo nữa, mà làm ba việc:

① Xác định danh mục đang có vấn đề
Từ nhật ký thói quen và dữ liệu sức khỏe cứng. Kết quả chỉ dùng để chọn nhóm mẹo — không dựng thẻ cảnh báo.
② Chọn mẹo xoay vòng theo ngày
Từ kho mẹo của danh mục đó (SuggestionCatalog) ⇒ feed luôn đổi mới; người dùng thấy nhiều gợi ý liên quan khác nhau thay vì một lời nhắc lặp lại.
③ Xếp thứ tự và giới hạn
Danh mục đang có vấn đề lên đầu, rồi tới các danh mục còn lại mà người dùng có thói quen (luôn có gợi ý tích cực để cải thiện), cuối cùng giới hạn 4 thẻ.

3.2. Hàm chính

fun generateSuggestions(
    activeHabits: List<Habit>,
    recentLogs: List<HabitLog>,
    healthHistory: List<HealthData> = emptyList(),
    rotationSeed: Int = defaultRotationSeed()      // = LocalDate.now().dayOfYear
): List<Suggestion> {

    val flagged = flaggedCategories(recentLogs, healthHistory)

    // Danh mục gợi ý = danh mục người dùng có thói quen ∪ danh mục đang có vấn đề.
    // App mới (chưa có gì) → mở toàn bộ kho mẹo để có gợi ý khởi đầu.
    val userCategories = activeHabits.map { it.category }.toSet()
    val relevant = SuggestionCatalog.categories.filter { it in userCategories || it in flagged }
        .ifEmpty { SuggestionCatalog.categories }

    // Danh mục đang có vấn đề LÊN ĐẦU để lời khuyên sát vấn đề hiện tại hơn
    val ordered = relevant.sortedByDescending { it in flagged }

    return ordered.mapIndexed { offset, category ->
        val focus = if (category in flagged) TipFocus.CONCERN else TipFocus.GENERAL
        val pool = if (focus == CONCERN) SuggestionCatalog.concernTips(category)
                   else SuggestionCatalog.generalTips(category)

        // ⭐ Xoay vòng: cùng một ngày thì kết quả ỔN ĐỊNH, sang ngày mới thì đổi mẹo
        val tipIndex = Math.floorMod(rotationSeed + offset, pool.size)
        pool[tipIndex].toSuggestion(id = category.ordinal * 100L + tipIndex)
    }
        .sortedByDescending { it.priority.ordinal }
        .take(MAX_SUGGESTIONS)                          // 4
}
Vì sao floorMod mà không phải %

rotationSeed + offset luôn dương ở đây, nhưng Math.floorMod là cách viết an toàn cho phép lấy modulo với số âm. Quan trọng hơn: offset (vị trí của danh mục trong danh sách đã xếp) được cộng vào seed, nên hai danh mục khác nhau sẽ chọn mẹo ở vị trí khác nhau — feed không bị "cùng một mẹo thứ nhất" cho mọi danh mục.

rotationSeed được truyền vào dưới dạng tham số (mặc định là ngày trong năm) chính để test được tất định: test truyền số cố định, không phụ thuộc ngày chạy.

3.3. Xác định danh mục "đang có vấn đề" — flaggedCategories

Có năm luật, hai nhóm nguồn dữ liệu:

private fun flaggedCategories(recentLogs: List<HabitLog>, healthHistory: List<HealthData>): Set<HabitCategory> {
    val flagged = mutableSetOf<HabitCategory>()

    // ── TỪ NHẬT KÝ THÓI QUEN (người dùng tự ghi) ────────────────────────────
    val recentSleep = recentLogs.filter { it.category == SLEEP }.sortedByDescending { it.loggedAt }.take(7)
    if (recentSleep.size >= MIN_LOGS_FOR_TREND && recentSleep.averageOf { it.value.toDouble() } < SLEEP_ENOUGH_HOURS)
        flagged += HabitCategory.SLEEP

    val recentWater = recentLogs.filter { it.category == WATER }.sortedByDescending { it.loggedAt }.take(7)
    if (recentWater.size >= MIN_LOGS_FOR_TREND && recentWater.averageOf { it.value.toDouble() } < WATER_ENOUGH_ML)
        flagged += HabitCategory.WATER

    if (isExerciseBelowTarget(recentLogs)) flagged += HabitCategory.EXERCISE

    // ── TỪ DỮ LIỆU SỨC KHỎE CỨNG (Health Connect / cảm biến của máy) ────────
    val dailyHistory = latestRowPerDay(healthHistory)      // gom về 1 hàng / ngày, mới → cũ

    // Thiếu ngủ: 3 NGÀY LIÊN TIẾP, mỗi ngày đều có số và đều < 6 giờ
    val recent3Sleep = dailyHistory.take(3)
    if (recent3Sleep.size >= 3 &&
        areConsecutiveDays(recent3Sleep.map { it.localDate() }) &&
        recent3Sleep.all { it.sleepHours > 0.0 && it.sleepHours < SLEEP_DEPRIVED_HOURS })
        flagged += HabitCategory.SLEEP

    // Ít vận động: 3 NGÀY LIÊN TIẾP đều có số và đều < 3000 bước
    val recentSteps = dailyHistory.take(STEP_TREND_DAYS)
    if (recentSteps.size >= STEP_TREND_DAYS &&
        areConsecutiveDays(recentSteps.map { it.localDate() }) &&
        recentSteps.all { it.steps > 0L && it.steps < STEP_TREND_LOW })
        flagged += HabitCategory.EXERCISE

    // Nhịp tim cao: trung bình 7 hàng đầu (chỉ tính hàng có nhịp) > 85 bpm
    val heartRateRows = dailyHistory.take(7).filter { it.heartRate > 0.0 }
    if (heartRateRows.isNotEmpty() && heartRateRows.averageOf { it.heartRate } > HEART_RATE_HIGH_BPM)
        flagged += HabitCategory.MINDFULNESS

    return flagged
}

3.4. Vận động: tại sao phải phân biệt "bước" và các đơn vị khác

Ngưỡng 5 000 / 8 000 bước chỉ có nghĩa với đơn vị bước. Trước đây engine so value với 5 000/8 000 bất kể đơn vị, nên một thói quen "Chạy bộ 30 phút" ghi 10 bị đọc thành "10 bước" và bị gắn cờ thiếu vận động. Logic hiện tại tách hai đường: 

private fun isExerciseBelowTarget(exerciseLogs: List<HabitLog>): Boolean {
    val byNewestFirst = exerciseLogs.filter { it.category == EXERCISE }.sortedByDescending { it.loggedAt }

    // ① Log đo bằng BƯỚC → dùng ngưỡng bước của WHO
    val stepLogs = byNewestFirst.filter { it.isStepUnit() }
    val recent5Steps = stepLogs.take(5)
    if (recent5Steps.size >= 5 && recent5Steps.all { it.value < STEP_DAILY_LOW }) return true
    val recent7Steps = stepLogs.take(7)
    if (recent7Steps.size >= 5 && recent7Steps.averageOf { it.value.toDouble() } < STEP_DAILY_RECOMMENDED) return true

    // ② Log đo đơn vị khác (phút, km, calo…) → so theo TỈ LỆ value / targetValueAtTime của chính thói quen
    val targetLogs = byNewestFirst.filterNot { it.isStepUnit() }
        .filter { it.targetValueAtTime > 0f }
        .take(5)
    if (targetLogs.size >= MIN_LOGS_FOR_TREND) {
        val avgRatio = targetLogs.averageOf { (it.value / it.targetValueAtTime).toDouble().coerceIn(0.0, 1.0) }
        if (avgRatio < TARGET_COMPLETION_MEDIUM) return true
    }

    return false
}

private fun HabitLog.isStepUnit(): Boolean = unit.trim().lowercase() in STEP_UNITS

3.5. Hai tiện ích dùng chung với giao diện

Hai hàm này cố ý giống hệt nhau giữa Rule Engine và thẻ "Lịch sử sức khỏe 7 ngày", để con số người dùng nhìn thấy và lý do AI gợi ý luôn khớp nhau: 

/** Mỗi ngày chỉ giữ HÀNG MỚI NHẤT — hàng đó là hàng đầy đủ dữ liệu nhất. */
private fun latestRowPerDay(history: List<HealthData>): List<HealthData> =
    history.groupBy { it.localDate() }
        .map { (_, rowsInDay) -> rowsInDay.maxByOrNull { it.recordedAt }!! }
        .sortedByDescending { it.recordedAt }

/** [days] phải theo thứ tự MỚI → CŨ và cách nhau ĐÚNG 1 ngày. */
private fun areConsecutiveDays(days: List<LocalDate>): Boolean =
    days.zipWithNext().all { (newer, older) -> ChronoUnit.DAYS.between(older, newer) == 1L }

areConsecutiveDays nhận danh sách đã sắp mới → cũ, nên vế between(older, newer) luôn là +1. Nếu đảo thứ tự, hàm trả false luôn — tức luật "3 ngày liên tiếp" sẽ không bao giờ chạy. Comment trong code ghi rõ yêu cầu thứ tự này.

5.2. Hai quyết định thiết kế then chốt

① Tính theo TỪNG NGÀY, không lấy trung bình cả tuần

Điểm là trung bình của điểm từng ngày trong cửa sổ 7 ngày — mỗi ngày có trọng số như nhau. Nhờ vậy điểm phản ánh đúng hiện tại: ngày không ghi gì / không đi bộ / không có giờ ngủ đóng góp 0 cho thành phần tương ứng ⇒ bỏ thói quen vài ngày là điểm tụt, thay vì giữ nguyên như khi lấy trung bình cả tuần.

② Chuẩn hoá lại trọng số khi thiếu nguồn dữ liệu

Chỉ tính các thành phần thực sự có nguồn trên máy, rồi chia cho weightSum (tổng trọng số của các thành phần có mặt). Ví dụ máy không có Health Connect và không bật cảm biến bước chân ⇒ chỉ còn thành phần thói quen với weightSum = 0.4; điểm không bị kéo xuống chỉ vì thiếu nguồn.

5.3. Code

fun compute(
    activeHabits: List<Habit>, habitLogs: List<HabitLog>, healthHistory: List<HealthData>,
    today: LocalDate, zone: ZoneId = ZoneId.systemDefault(), windowDays: Int = WINDOW_DAYS
): Int? {                                   // null = "chưa đủ dữ liệu để chấm điểm"
    val window = windowOf(today, windowDays)                 // cũ → mới, kết thúc ở today
    val rowsByDate = healthHistory.groupBy { capturedDate(it, zone) }

    // Thành phần nào THỰC SỰ có nguồn trên máy?
    val hasHabits = activeHabits.isNotEmpty()
    val hasSleep = window.any { date -> rowsByDate[date].orEmpty().any { it.sleepHours > 0.0 } }
    val hasSteps = window.any { date -> rowsByDate[date].orEmpty().any { it.steps > 0L } }

    // Không có gì để chấm → null (UI hiện lời nhắc thay vì một con số ảo)
    if (!hasHabits && !hasSleep && !hasSteps) return null

    val weightSum = (if (hasHabits) HABIT_WEIGHT else 0.0) +
        (if (hasSleep) SLEEP_WEIGHT else 0.0) +
        (if (hasSteps) STEPS_WEIGHT else 0.0)

    val dayScores = window.map { date ->
        val dayLogs = habitLogs.filter { it.loggedAt in dayOf(date, zone) }

        var acc = 0.0
        if (hasHabits) acc += HABIT_WEIGHT * habitCompletion(activeHabits, dayLogs)
        if (hasSleep) {
            val hours = rowsByDate[date].orEmpty().latest()?.sleepHours ?: 0.0
            acc += SLEEP_WEIGHT * ratio(hours, SLEEP_TARGET_HOURS)
        }
        if (hasSteps) {
            val steps = rowsByDate[date].orEmpty().latest()?.steps ?: 0L
            acc += STEPS_WEIGHT * ratio(steps.toDouble(), STEPS_TARGET)
        }
        acc / weightSum                              // điểm của ngày đó ∈ 0..1
    }

    return Math.round(dayScores.average() * 100.0).toInt().coerceIn(0, 100)
}

/** Tỉ lệ thói quen ĐẠT MỤC TIÊU trong ngày: tổng value của các log cùng habitId >= targetValue */
private fun habitCompletion(habits: List<Habit>, dayLogs: List<HabitLog>): Double {
    if (habits.isEmpty()) return 0.0
    val completed = habits.count { habit ->
        dayLogs.filter { it.habitId == habit.id }.sumOf { it.value.toDouble() } >= habit.targetValue
    }
    return completed.toDouble() / habits.size
}

private fun ratio(value: Double, target: Double): Double =
    if (target <= 0.0) 0.0 else (value / target).coerceIn(0.0, 1.0)

Lưu ý: mỗi ngày lấy hàng mới nhất (latest() = maxByOrNull { it.recordedAt }) — hàng mới nhất trong ngày là hàng đầy đủ dữ liệu nhất.

5.4. Delta so với tuần trước

GetVitalityScoreUseCase đọc 14 ngày (7 ngày tuần này + 7 ngày tuần trước), tính điểm hiện tại, rồi tính điểm của cửa sổ kết thúc ở today − 7 để lấy hiệu số.

6. Gom dữ liệu theo ngày — ba hàm thuần

Ba hàm nhỏ nhưng là nền tảng của mọi con số ở tab Phân tích. Chúng tồn tại riêng để giao diện, AI và biểu đồ dùng cùng một con số.

6.1. HealthSummaryHistory — lịch sử 7 ngày

fun summarize(history: List<HealthData>, days: Int = 7, today: LocalDate, zone: ZoneId): List<DailyHealthSummary> {
    val windowDays = days.coerceAtLeast(1)

    // Quy tắc 1: mỗi ngày chỉ lấy HÀNG MỚI NHẤT (giống HabitRuleEngine.latestRowPerDay)
    val latestRowPerDay = history
        .groupBy { Instant.ofEpochMilli(it.recordedAt).atZone(zone).toLocalDate() }
        .mapValues { (_, rowsInDay) -> rowsInDay.maxBy { it.recordedAt } }

    // Quy tắc 2: LUÔN trả đủ [days] dòng, kể cả ngày không có dữ liệu (hasData = false)
    return (windowDays - 1 downTo 0).map { daysAgo ->
        val date = today.minusDays(daysAgo.toLong())
        val row = latestRowPerDay[date]
        DailyHealthSummary(
            date = date,
            steps = row?.steps ?: 0L,
            sleepHours = row?.sleepHours ?: 0.0,
            heartRate = row?.heartRate ?: 0.0
        )
    }
}

Hai quy tắc này giải quyết hai vấn đề cụ thể của giao diện:

  • Luôn đủ 7 dòng ⇒ biểu đồ và bảng không bị co lại thành vài ngày rời rạc khi máy thiếu nguồn dữ liệu vài hôm.
  • Ngày trống có hasData = false ⇒ UI hiện "Chưa có dữ liệu" thay vì một loạt số 0 gây hiểu nhầm ("ngày đó đi bộ 0 bước").

Thứ tự trả về là cũ → mới (trái sang phải khi vẽ), cùng chiều với GetWeeklyConsistencyUseCase.

6.2. SleepTrendMath — xu hướng giấc ngủ

fun qualityOf(averageHours: Double): SleepQuality = when {

6.3. TodayHealthSummary — nguồn duy nhất cho "hôm nay"

Đây là model quan trọng nhất của quy tắc ưu tiên nguồn cho widget. Lưu ý: thẻ "Tóm tắt sức khỏe" ở Trang chủ nay theo switch "Dùng dữ liệu Health Connect" (mặc định TẮT → dùng bản chụp trong app) nên có thể khác widget khi switch TẮT. Nó gói toàn bộ quy tắc ưu tiên nguồn vào một hàm thuần: 

data class TodayHealthSummary(val steps: Long, val sleepHours: Double, val heartRateBpm: Double) {
    companion object {
        fun build(
            healthConnect: HealthData?,      // null khi Health Connect không khả dụng / chưa đủ quyền
            sensorStepsReady: Boolean,
            sensorSteps: Long,
            sensorSleepHours: Double,
            recordedHeartRate: Double

            // BƯỚC CHÂN: ưu tiên CẢM BIẾN CỦA ĐIỆN THOẠI — vì đó là nguồn live
            steps = if (sensorStepsReady) sensorSteps else healthConnect?.steps ?: 0L,
            // GIẤC NGỦ: ưu tiên HEALTH CONNECT — có thể đến từ đồng hồ đeo tay
            sleepHours = (healthConnect?.sleepHours ?: 0.0).takeIf { it > 0.0 } ?: sensorSleepHours,
            // NHỊP TIM: ưu tiên HEALTH CONNECT — chưa có thì dùng nhịp GHI TRONG NGÀY
            heartRateBpm = (healthConnect?.heartRate ?: 0.0).takeIf { it > 0.0 } ?: recordedHeartRate
        )
    }
}
Chiều ưu tiên của bước chân là ngược với hai chỉ số kia — và đó là chủ ý

healthData chỉ được đọc một lần lúc mở màn Home. Nếu để Health Connect ưu tiên cho bước chân thì con số trên thẻ sẽ bị "đóng băng" — đi bộ mà số không đổi cho tới khi ViewModel được tạo lại. Còn giấc ngủ thì không đổi trong ngày (giấc ngủ của đêm đã qua), nên việc chỉ đọc một lần không gây hậu quả.

Đánh đổi đã chấp nhận: khi máy có cảm biến thì số của đồng hồ đeo tay (nằm trong Health Connect) không còn được ưu tiên cho bước chân.

7. Biểu đồ tuần — GetWeeklyConsistencyUseCase

domain/usecase/habit/GetWeeklyConsistencyUseCase.kt

Tính mức hoàn thành thói quen theo từng ngày trong 7 ngày gần nhất, trả về DailyConsistency theo thứ tự cũ → mới. 

val today = LocalDate.now(zone)
/* … */
(val windowDays - 1 downTo 0).map { daysAgo ->
    val date = today.minusDays(daysAgo.toLong())
    val dayStart = date.atStartOfDay(zone).toInstant().toEpochMilli()
    val dayEnd = date.plusDays(1).atStartOfDay(zone).toInstant().toEpochMilli()

    val dayLogs = logs.filter { it.loggedAt >= dayStart && it.loggedAt < dayEnd }

    // ⭐ MẪU SỐ LÀ "SNAPSHOT" CỦA TỪNG NGÀY:
    //    chỉ tính những thói quen ĐÃ TỒN TẠI trong ngày đó (createdAt < mốc kết thúc ngày)
    val habitsOfThatDay = habits.filter { it.createdAt < dayEnd }

    val completed = habitsOfThatDay.count { habit ->
        dayLogs.filter { it.habitId == habit.id }.sumOf { it.value.toDouble() } >= habit.targetValue
    }

    DailyConsistency(date = date, completedHabits = completed, totalHabits = habitsOfThatDay.size)
}
Vì sao mẫu số phải là "snapshot theo ngày"

Trước đây mẫu số luôn là số thói quen đang hoạt động hiện tại. Hệ quả: tạo thói quen mới hôm nay sẽ làm tụt tỉ lệ của cả 6 ngày trước đó (vì mẫu số tăng trong khi tử số không đổi), và xoá thói quen sẽ làm tỉ lệ quá khứ vọt lên. Biểu đồ không còn phản ánh đúng lịch sử.

Nay mỗi ngày chỉ tính những thói quen đã tồn tại từ ngày đó trở về trước (createdAt < dayEnd).

Ghi chú: mục tiêu vẫn so với Habit.targetValue hiện tại (không dùng targetValueAtTime của từng log) — giữ nguyên nghiệp vụ cũ, chỉ sửa mẫu số.

fun toInsight(isFood: Boolean, dishName: String?, emoji: String?, benefits: List<String>?, cautions: List<String>?): FoodInsight {
    if (!isFood) return FoodInsight()                          // ảnh không có đồ ăn

    val name = dishName.orEmpty().trim().take(MAX_DISH_NAME_LENGTH)   // 60
    if (name.isEmpty()) return FoodInsight()                    // nói có đồ ăn mà không gọi được tên

    return FoodInsight(
        isFood = true, dishName = name,
        emoji = sanitizeEmoji(emoji),
        benefits = sanitizeBullets(benefits),
        cautions = sanitizeBullets(cautions)
    )
}

/** Emoji hợp lệ, hoặc DEFAULT_EMOJI ("🍽️") khi thiếu/rỗng/quá dài (khả năng cao là văn bản) */
private fun sanitizeEmoji(emoji: String?): String {
    val trimmed = emoji.orEmpty().trim()
    return if (trimmed.isEmpty() || trimmed.length > 8) DEFAULT_EMOJI else trimmed
}

/** Cắt khoảng trắng → bỏ mục rỗng → cắt độ dài → bỏ trùng → giới hạn 3 mục */
private fun sanitizeBullets(bullets: List<String>?): List<String> =
    bullets.orEmpty()
        .map { it.trim().take(MAX_BULLET_LENGTH) }   // 120
        .filter { it.isNotEmpty() }
        .distinct()
        .take(MAX_BULLETS)                            // 3

8.5. Chiến lược gọi model: model chính + model dự phòng

Đây là phần được tinh chỉnh qua nhiều lần chạy thật. Bốn quyết định:

① Hạ mức suy luận để giảm độ trễ
Gemini 3 mặc định suy luận ở mức high — một lượt đọc ảnh mất ~42 giây. Dự án hạ xuống thinkingConfig.thinkingLevel = "low". Mức "minimal" bị model này từ chối (400 INVALID_ARGUMENT), nên "low" là mức thấp nhất dùng được.
② Model không nhận thinkingConfig ⇒ tự gửi lại không kèm tham số đó
Nhận biết theo nội dung thông báo lỗi (chứa "thinking" và "INVALID_ARGUMENT"), không theo mã 400 đơn thuần — vì 400 còn do nhiều nguyên nhân khác.
③ Có model dự phòng cho lỗi quá tải
Google trả 503 UNAVAILABLE và 429 RESOURCE_EXHAUSTED rất thường xuyên. Thay vì thử lại chính model vừa hỏng, lớp gọi chuyển sang model nhẹ hơn (gemini-flash-lite-latest).
④ Lỗi không tự khỏi thì dừng luôn, không đổi model
Sai khoá (401/403) đổi model cũng vô ích ⇒ trả kết quả ngay để người dùng biết sớm thay vì chờ. 
override suspend fun analyze(jpegBytes: ByteArray): FoodAnalysisResult {
    if (apiKey.isBlank()) return FoodAnalysisResult.Failure(FoodAnalysisError.NOT_CONFIGURED)
    val jpegBase64 = Base64.getEncoder().encodeToString(jpegBytes)

    val models = candidates()             // [model chính, model dự phòng] — bỏ rỗng và trùng
    var lastError = FoodAnalysisError.NETWORK
    models.forEachIndexed { index, candidate ->
        when (val result = analyzeWithModel(candidate, jpegBase64)) {
            is FoodAnalysisResult.Success -> return result
            is FoodAnalysisResult.Failure -> {
                lastError = result.error
                // Lỗi KHÔNG thể tự khỏi (sai khoá, sai model…) thì đổi model cũng vô ích
                if (result.error !in RETRYABLE_ERRORS) return result
                if (index < models.lastIndex) delay(RETRY_DELAY_MS)    // 600 ms
            }
        }
    }
    return FoodAnalysisResult.Failure(lastError)
}

8.6. Tên model không hardcode

Tên model đọc từ GEMINI_MODEL / GEMINI_FALLBACK_MODEL, tức từ local.properties lúc build. Lý do có thật: Google bỏ tên model cũ và trả 404 kèm gợi ý model mới. Đổi tên model chỉ cần sửa local.properties, không phải sửa code Kotlin.

Ngoài ra còn một "bẫy build" đã gặp: CameraX trả về ListenableFuture của Guava, nhưng Gradle chọn bản jar rỗng listenablefuture:9999.0-empty-to-avoid-conflict-with-guava nên Kotlin không biên dịch được. Module này được ép về bản 1.0 bằng resolutionStrategy.force.

9. Cổng riêng tư: khi nào nhật ký được phép rời máy?

domain/usecase/sync/CloudSyncPolicy.kt

Vấn đề thật đã xảy ra

SyncWorker trước đây đẩy mọi log có isDirty = true lên đám mây ngay khi có phiên đăng nhập — mà mọi log mặc định đều isDirty = true. Nên một người dùng đã ghi nhật ký ở chế độ khách rồi đăng nhập sẽ bị đẩy toàn bộ lịch sử lên đám mây mà không hề được hỏi.

Nay việc tải lên phải qua hai điều kiện, và cả hai đều nằm ở một hàm thuần duy nhất:

fun logsToUpload(logs: List<HabitLog>, settings: CloudSyncSettings): List<HabitLog> {
    if (!settings.enabled) return emptyList()                    // ① người dùng chưa BẬT đồng bộ
    val consentAt = settings.consentAtMillis ?: return emptyList()  // ② thiếu mốc đồng ý → hướng an toàn
    return logs.filter { it.loggedAt >= consentAt }                // ③ chỉ log tạo SAU khi đồng ý
}
