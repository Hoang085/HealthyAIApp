2. Room + SQLCipher

Tên file: healthy_ai_encrypted.db. Cả DB được mã hoá AES-256 bởi SQLCipher; Room không biết mình đang chạy trên DB mã hoá — ta chỉ đưa vào một SupportOpenHelperFactory(passphrase.bytes).

Bảng này được thiết kế để gộp theo ngày, không phải ghi mới mỗi lần sync:

// HealthDataRepositoryImpl.upsertToday() — 1 hàng cho mỗi NGÀY, không phải mỗi lần sync
val existing = healthDataDao.getLatestSince(startOfToday())

if (existing == null) {
    healthDataDao.insertHealthData(HealthDataEntity.fromDomain(snapshot))
    return
}

healthDataDao.updateHealthData(
    existing.copy(
        // Bước chân CHỈ TĂNG trong ngày ⇒ lấy số lớn hơn để lần sync sau không làm tụt số
        steps = maxOf(existing.steps, snapshot.steps),
        // Các chỉ số khác lấy giá trị MỚI nếu có số, nếu không thì GIỮ số cũ.
        // Nhờ vậy lần sync thiếu quyền Health Connect không xoá mất dữ liệu đã ghi trước đó.
        sleepHours = if (snapshot.sleepHours > 0.0) snapshot.sleepHours else existing.sleepHours,
        heartRate = if (snapshot.heartRate > 0.0) snapshot.heartRate else existing.heartRate,
        activeCalories = if (snapshot.activeCalories > 0.0) snapshot.activeCalories else existing.activeCalories,
        recordedAt = System.currentTimeMillis()
    )
)

Dọn dẹp: mỗi lần sync gọi deleteOldData(now − 30 ngày) — giữ 30 ngày lịch sử. Không ghi hàng toàn số 0 để không làm nhiễu phân tích của Rule Engine.

3. Migration — nâng cấp schema không mất dữ liệu

Bối cảnh: vì sao migration quan trọng ở đây

Trước đây DatabaseModule dùng fallbackToDestructiveMigration(): mỗi lần tăng version, Room xoá sạch mọi bảng rồi tạo lại ⇒ người dùng mất toàn bộ thói quen và nhật ký. Nay đã bỏ hẳn; mỗi bước tăng version có một Migration giữ nguyên dữ liệu.

3.1. Bản đồ version

1habits chưa có timeOfDay/frequency; habit_logs chưa có targetValueAtTime; chưa có health_data_history—
2Thêm 3 cột trênMIGRATION_1_2
3Thêm bảng health_data_historyMIGRATION_2_3

3.2. MIGRATION_1_2 — thêm cột và backfill

ALTER TABLE `habits` ADD COLUMN `timeOfDay` TEXT NOT NULL DEFAULT 'ALL_DAY'
ALTER TABLE `habits` ADD COLUMN `frequency` TEXT NOT NULL DEFAULT 'DAILY'
ALTER TABLE `habit_logs` ADD COLUMN `targetValueAtTime` REAL NOT NULL DEFAULT 0

-- Log cũ chưa lưu mục tiêu tại thời điểm ghi.
-- Nếu để 0, "Chỉ số sinh lực" sẽ tính toàn bộ dữ liệu TRƯỚC khi nâng cấp thành 0%.
-- ⇒ lấy mục tiêu hiện tại của chính thói quen đó để backfill.
UPDATE `habit_logs`
SET `targetValueAtTime` = COALESCE(
    (SELECT `targetValue` FROM `habits` WHERE `habits`.`id` = `habit_logs`.`habitId`),
    0
)
WHERE `targetValueAtTime` = 0

Hai giá trị mặc định được chọn để khớp đúng ngữ nghĩa trước khi nâng cấp: mọi thói quen cũ đều được hiểu là "Cả ngày" và "Hàng ngày".

3.3. MIGRATION_2_3 và MIGRATION_3_4

Chỉ tạo bảng mới — hai câu DDL phải khớp từng ký tự với createSql mà Room sinh ra trong app/schemas/…/3.json và 4.json:

-- 2 → 3

Vì sao DDL phải khớp chính xác

Room kiểm tra schema sau khi chạy migration. Lệch một ký tự (khoảng trắng, thứ tự cột, NOT NULL) sẽ làm Room báo Migration didn't properly handle: app_settings khi mở DB. Repo lưu schema JSON ở app/schemas/com.healthyai.app.data.local.AppDatabase/ (1.json…4.json) chính là để đối chiếu việc này.

3.4. Hai quy tắc khi thêm version mới

  1. Các câu lệnh chỉ dùng ALTER TABLE … ADD COLUMN … DEFAULT hoặc CREATE TABLE — không DROP/RENAME bảng. Giữ nguyên bảng habit_logs (đang có FK CASCADE) nên không có nguy cơ mất log.
  2. Tăng version ở AppDatabase, thêm migration vào DatabaseMigrations.ALL, cập nhật DatabaseMigrations.DATABASE_VERSION. Test DatabaseMigrationsTest sẽ fail nếu dãy migration bị thiếu bước.

Cách kiểm chứng không cần emulator: dựng DB ở version cũ bằng sqlite3 từ schema cũ, chạy các câu lệnh migration, rồi so PRAGMA table_info / index_list / foreign_key_list với schema mới.

4. Bảo mật: khoá DB không còn nằm trong APK

Trước đây passphrase SQLCipher là hằng số viết cứng "REPLACE_WITH_SECURE_KEY_FROM_KEYSTORE" ngay trong APK ⇒ bất kỳ ai có file healthy_ai_encrypted.db (máy root, adb backup, file sao lưu) đều mở được. Cơ chế hiện tại gồm bốn mảnh ghép.

4.1. Pipeline lấy passphrase

DatabaseModule → DatabasePassphraseProvider.getOrCreate() → SharedPreferencesPassphraseVault
healthy_ai_secure_store ↔ AndroidKeystorePassphraseCipher
AES-256/GCM 
fun getOrCreate(): DatabasePassphrase {
    val stored = vault.read()
    if (stored != null) {
        try {
            // Máy đã có passphrase ⇒ đọc lại đúng khoá cũ (KHÔNG sinh khoá mới)
            return DatabasePassphrase(cipher.decrypt(stored), newlyCreated = false)
        } catch (_: GeneralSecurityException) {
            // Khoá Keystore mất/không giải mã được ⇒ rơi xuống nhánh sinh mới
        }
    }

    // Lần chạy đầu (hoặc khoá Keystore đã mất): sinh 32 byte ngẫu nhiên
    val fresh = ByteArray(PASSPHRASE_LENGTH_BYTES).also(random::nextBytes)
    // Ghi TRƯỚC khi trả khoá về tầng gọi — vault.commit() đồng bộ
    vault.write(cipher.encrypt(fresh))
    return DatabasePassphrase(fresh, newlyCreated = true)
}

4.2. Bốn mảnh ghép bảo mật

🔑

Khoá sinh ngẫu nhiên

32 byte = 256-bit entropy từ SecureRandom, khớp chuẩn AES-256 của SQLCipher. Sinh một lần cho mỗi máy.

🛡️

Bọc bằng Android Keystore

Alias healthy_ai_sqlcipher_key_v1, khoá AES-256/GCM sinh trong Keystore. Khoá không rời khỏi thiết bị (có TEE/Secure Element thì không rời phần cứng).

💾

Chỉ lưu bản mã

Prefs chỉ chứa Base64(IV ‖ ciphertext+tag). Mỗi lần ghi ra bản mã khác nhau (IV 12 byte, tag 128 bit).

🚫

Không log khoá

DatabasePassphrase.toString() cố tình in DatabasePassphrase(***, …) để khoá không lọt vào log/crash report.

Vì sao ghi prefs bằng commit() mà không phải apply()

Passphrase được lưu ngay trước khi Room tạo/mở file DB. Nếu tiến trình bị hệ thống kill trong lúc bản ghi còn nằm trong hàng đợi bất đồng bộ của apply(), lần mở sau sẽ không tìm thấy passphrase ⇒ sinh khoá mới ⇒ DB cũ không mở được nữa và bị xoá ⇒ mất dữ liệu. Ghi đồng bộ loại bỏ đúng khe thời gian này; chi phí chỉ là một lần ghi file XML rất nhỏ, xảy ra ở lần chạy đầu hoặc khi khoá Keystore đã mất.

4.3. Rekey DB của bản cũ — LegacyDatabaseKeyMigration

Máy đã cài bản cũ vẫn còn file DB mã hoá bằng khoá hard-code. Mở bằng khoá mới sẽ lỗi "file is not a database"; fallbackToDestructiveMigration() không cứu được (nó chỉ xử lý lệch version schema, mà version ở đây không đổi) ⇒ app crash vĩnh viễn. Cách xử lý: đúng một lần trên mỗi máy, mở DB cũ bằng khoá cũ rồi PRAGMA rekey sang khoá mới. 

private fun rekey(path: String, newPassphrase: ByteArray) {
    val database = SQLiteDatabase.openDatabase(
        path, LEGACY_PASSPHRASE.toByteArray(Charsets.UTF_8), null,
        SQLiteDatabase.OPEN_READWRITE, null
    )
    try {
        database.execPragma("PRAGMA wal_checkpoint(TRUNCATE)")  // ① đẩy hết frame WAL vào file chính
        database.execPragma("PRAGMA journal_mode=DELETE")     // ② thoát WAL (rekey khi còn frame
                                                          //    trong WAL có thể trộn trang khoá cũ/mới → hỏng DB)
        database.changePassword(newPassphrase)             // ③ đổi khoá
        database.execPragma("PRAGMA journal_mode=WAL")        // ④ bật lại WAL như Room vẫn dùng
    } finally {
        database.close()
    }
}

Hàm được gọi chỉ khi newlyCreated == true (lúc đó mọi file DB còn sót lại chắc chắn thuộc bản cũ). Nếu rekey thất bại (file hỏng, DB do bản build khác tạo) thì xoá DB để tạo mới sạch — mất dữ liệu cục bộ, nhưng tránh vòng lặp crash. Theo dõi bằng adb logcat -s DatabaseKeyMigration.

4.4. allowBackup="false"

Manifest đặt android:allowBackup="false" một cách có chủ ý: DB SQLCipher và prefs bị auto-backup lên Google Drive, nhưng khoá mở DB nằm trong Android Keystore — không backup được. Restore trên máy mới sẽ mở DB thất bại và rơi vào nhánh xoá DB ⇒ mất sạch dữ liệu. Tắt hẳn backup vừa tránh bản sao rò rỉ dữ liệu sức khỏe, vừa tránh một lần "restore" xoá dữ liệu của người dùng.

5.2. Chi tiết pha giấc ngủ — hai mức phân giải

Không phải thiết bị nào cũng chia pha giấc ngủ. getSleepStageBreakdown() đọc SleepSessionRecord và phân loại theo từng phiên: 

response.records.forEach { session ->
    var sessionHasStages = false
    session.stages.forEach { stage ->
        val minutes = Duration.between(stage.startTime, stage.endTime).toMinutes()
        when (stage.stage) {
            STAGE_TYPE_DEEP  -> { deepMinutes  += minutes; sessionHasStages = true }
            STAGE_TYPE_LIGHT -> { lightMinutes += minutes; sessionHasStages = true }
            STAGE_TYPE_REM   -> { remMinutes   += minutes; sessionHasStages = true }
        }
    }

    if (!sessionHasStages) {
        // Phiên ngủ KHÔNG chia pha (STAGE_TYPE_SLEEPING/UNKNOWN…) — trước đây bị bỏ qua
        // hoàn toàn nên thẻ giấc ngủ hiện trạng thái rỗng dù Health Connect CÓ dữ liệu.
        unstagedMinutes += Duration.between(session.startTime, session.endTime).toMinutes()
    }
}

Kết quả là SleepStageBreakdown với deep/light/rem và unstagedMinutes. Hai cờ dẫn xuất phân biệt rạch ròi ba trạng thái: hasStages (máy chia pha), hasData (có dữ liệu ngủ, chia pha hoặc chỉ tổng thời lượng), và cả hai false (không có dữ liệu ngủ).

Lưu ý thiết kế: phiên chia pha chỉ tính theo pha để không cộng trùng cùng một khoảng thời gian hai lần. Dữ liệu này đọc trực tiếp từ Health Connect, không qua Room — nhờ vậy không cần thêm cột vào schema.

7. Cổng HTTP ra ngoài

Chỉ có một cổng ra mạng, và nó cố ý đơn giản nhất có thể: HttpURLConnection của JDK thay vì thêm OkHttp (yêu cầu chỉ là một POST JSON). 

class HttpUrlConnectionPost @Inject constructor() : HttpPost {
    override suspend fun post(url: String, headers: Map<String, String>, body: String): HttpPostResponse? =
        withContext(Dispatchers.IO) {          // ⚠ I/O mạng: gọi từ Main thread sẽ ném NetworkOnMainThreadException
            var connection: HttpURLConnection? = null
            try {
                connection = (URL(url).openConnection() as HttpURLConnection).apply {
                    requestMethod = "POST"
                    connectTimeout = 15_000
                    readTimeout = 60_000     // ảnh gửi kèm nên phản hồi có thể lâu
                    doOutput = true
                    setRequestProperty("Content-Type", "application/json; charset=utf-8")
                    headers.forEach { (name, value) -> setRequestProperty(name, value) }
                }
                connection.outputStream.use { it.write(body.toByteArray(Charsets.UTF_8)) }

                val code = connection.responseCode
                // Lỗi HTTP nằm ở errorStream, không phải inputStream — vẫn đọc để biết lý do thật
                val stream = if (code in 200..299) connection.inputStream else connection.errorStream
                val text = stream?.bufferedReader(Charsets.UTF_8)?.use { it.readText() }.orEmpty()
                HttpPostResponse(code, text)
            } catch (e: CancellationException) {
                throw e                                        // đúng quy ước của repo
            } catch (e: Exception) {
                null          // mất mạng / DNS / timeout ⇒ null, phân biệt với "server trả lỗi"
            } finally {
                connection?.disconnect()
            }
        }
}

Hợp đồng rõ ràng: null = không gọi được; HttpPostResponse(code, body) = đã gọi được (kể cả khi code là 500). Nhờ vậy GeminiFoodInsightSource tách được lỗi mạng khỏi lỗi nghiệp vụ.

📷

Ảnh chụp qua CameraX

Đi thẳng vào ImageJpegEncoder.encode(bitmap): thu nhỏ cạnh dài ≤ 1280 px (nếu cần) + nén JPEG chất lượng 80, chạy trên Dispatchers.Default.

Ảnh chọn từ thư viện

Qua GalleryImageLoader.load() trước: đọc kích thước bằng inJustDecodeBounds, tính inSampleSize (luỹ thừa 2) rồi mới giải mã, cuối cùng xoay theo EXIF.

// GalleryImageLoader — hai bước bắt buộc với ảnh trong thư viện

// ① Đọc kích thước TRƯỚC khi giải mã (không tốn bộ nhớ)
val bounds = BitmapFactory.Options().apply { inJustDecodeBounds = true }
resolver.openInputStream(uri)?.use { BitmapFactory.decodeStream(it, null, bounds) }

// ② Tính hệ số thu nhỏ (luỹ thừa 2 — đúng yêu cầu của BitmapFactory) rồi mới giải mã
private fun sampleSizeFor(width: Int, height: Int, maxDimension: Int): Int {
    var sample = 1
    while (max(width, height) / (sample * 2) >= maxDimension) sample *= 2
    return sample
}

// ③ Xoay theo cờ EXIF: ảnh chụp dọc thường lưu dạng NGANG kèm cờ orientation;
//    thiếu bước này thì món ăn bị quay 90° khi AI phân tích.

1280 px đủ để mô hình nhận ra món ăn mà vẫn nhẹ: ảnh 4:3 còn ~1,3 MP (~5 MB trong bộ nhớ) so với ~48 MB của ảnh 12 MP nguyên bản. Cả hai lớp dùng chung hằng số 1280 px để mọi đường vào đều qua cùng một chuẩn.

Điểm quan trọng về riêng tư: ảnh không được lưu ra đĩa. CameraViewModel chỉ giữ một ByteArray JPEG của lượt phân tích gần nhất trong RAM (để nút "Thử lại" chạy lại được), và xoá nó khi rời màn.

9. Ba cảm biến của máy

9.1. AndroidStepCounterSensor — TYPE_STEP_COUNTER

Chọn TYPE_STEP_COUNTER (không phải TYPE_STEP_DETECTOR) vì ba lý do: đếm ở phần cứng nên gần như không tốn pin và vẫn đếm khi màn hình tắt; không cần foreground service để giữ việc đếm khi chạy nền; và trả về giá trị luỹ kế nên tầng trên tự quyết định lấy phần nào.

Một cái bẫy Android đã được xử lý: thẻ xin quyền "không bao giờ hiện"

Từ Android 10, cảm biến bước chân bị ẩn với app chưa có quyền ACTIVITY_RECOGNITION: getDefaultSensor(TYPE_STEP_COUNTER) trả null. Nếu chỉ dựa vào đó thì isAvailable luôn false lúc chưa cấp quyền, và thẻ xin quyền ở màn Trang chủ không bao giờ hiện — người dùng rơi vào thế bế tắc "muốn cấp quyền phải thấy thẻ, muốn thấy thẻ phải có quyền". Vì vậy isAvailable kiểm thêm khả năng phần cứng qua PackageManager.FEATURE_SENSOR_STEP_COUNTER — cờ này không phụ thuộc quyền. 

override val isAvailable: Boolean
    get() = stepCounterSensor != null ||
        context.packageManager.hasSystemFeature(PackageManager.FEATURE_SENSOR_STEP_COUNTER)

Emulator (và một số máy rẻ tiền) không có cả cờ lẫn cảm biến ⇒ app không hiện thẻ xin quyền, và số bước vẫn lấy từ Health Connect.

9.2. AndroidSleepSensor — ánh sáng + gia tốc + màn hình

Ba tín hiệu, không cần quyền nào:

Tín hiệuNguồnCách đọc
Màn hình có đang được dùng?PowerManager.isInteractiveĐọc tức thời
Phòng có tối?Sensor.TYPE_LIGHTGiá trị cuối cùng nhận được trong cửa sổ ngắn (LIGHT_SETTLE_MS)
Điện thoại có bất động?Sensor.TYPE_ACCELEROMETERĐộ lệch lớn nhất khỏi 1g trong cửa sổ lấy mẫu
 
private suspend fun readPeakMotion(manager: SensorManager, sensor: Sensor, windowMs: Long): Float {
    var peak = 0f
    val listener = object : SensorEventListener {
        override fun onSensorChanged(event: SensorEvent) {
            val magnitude = sqrt(x*x + y*y + z*z)
            // Dùng giá trị LỚN NHẤT (không phải trung bình) để một cử động ngắn
            // cũng đủ kết luận "đang thức".
            peak = max(peak, abs(magnitude - GRAVITY_M_S2))
        }
    }
    manager.registerListener(listener, sensor, SensorManager.SENSOR_DELAY_NORMAL)
    try {
        delay(windowMs.coerceAtLeast(MIN_SAMPLE_WINDOW_MS))
    } finally {
        manager.unregisterListener(listener)   // ⚠ gỡ listener KỂ CẢ khi coroutine bị huỷ
    }
    return peak
}

Nghe cảm biến liên tục sẽ tốn pin, nên lớp này chỉ lấy mẫu theo yêu cầu: nghe trong vài giây rồi gỡ listener. Nhờ vậy SleepTrackingWorker chạy thưa (15 phút/lần) mà không cần foreground service và không tốn pin suốt đêm.

Máy không có cảm biến ánh sáng ⇒ trả 0f (coi như "tối"); khi đó hai tín hiệu còn lại vẫn phải đúng mới kết luận là ngủ.

9.3. CameraPpgAnalyzer — đọc kênh đỏ từ khung hình

Đây là ImageAnalysis.Analyzer của CameraX. Mỗi khung hình, nó tính giá trị đỏ trung bình của vùng giữa khung — đúng vùng ngón tay che lên (đèn flash và ống kính nằm cạnh nhau ở mặt sau máy). 

override fun analyze(image: ImageProxy) {
    try {
        val red = meanRedOfCenterRoi(image)
        if (red != null) onSample(red, image.imageInfo.timestamp / NANOS_PER_MILLI)
    } finally {
        image.close()   // ⚠ bắt buộc: không close thì ImageAnalysis hết bộ đệm và DỪNG phát khung hình
    }
}

Ba tối ưu đáng chú ý:

  • Chỉ đọc hai mặt phẳng Y và V thay vì đổi cả khung sang RGB. Vì YUV→RGB là phép biến đổi tuyến tính, trung bình kênh đỏ suy được từ trung bình Y và V: R = Y + 1.402·(V − 128). Đổi từng điểm ảnh là thừa và chậm gấp nhiều lần ở 30 khung/giây.
  • Lấy mẫu cách 4 điểm ảnh (SAMPLE_STEP = 4): vùng giữa ở 640×480 là 320×240 điểm ⇒ còn 4 800 mẫu — thừa để tính trung bình mà vẫn kịp 30 fps trên máy yếu.
  • Giá trị trả về không bị cắt về 0..255: phần chênh lệch nhỏ giữa các khung hình mới là thứ cần đo, cắt biên sẽ làm mất đúng phần tín hiệu đó.

Toán quy đổi nằm ở HeartRateMath.redFromYuvMeans() (domain, test được JVM); phần đọc bộ đệm nằm ở đây (data, chạm Android). Xem thuật toán đầy đủ ở trang Thuật toán cảm biến.
