Chương 7

Chạy nền & phân quyền

Bốn WorkManager worker chạy định kỳ (đồng bộ sức khỏe, đồng bộ đám mây, nhắc nhở, lấy mẫu giấc ngủ), cùng toàn bộ quyền mà app xin và cách nó xin — gồm cả cơ chế rationale bắt buộc của Health Connect.

1. Tổng quan: bốn worker

SyncWorker 6 giờ Đẩy nhật ký thói quen chưa đồng bộ lên Firestore — chỉ khi đã bật đồng bộ và log tạo sau mốc đồng ý periodic_sync_worker

15 phút là khoảng định kỳ nhỏ nhất WorkManager cho phép — vì vậy SleepTrackingWorker không thể chạy dày hơn, và đó cũng là lý do SleepTrackerMath phải cộng toàn bộ khoảng giữa hai mẫu "đang ngủ".

Cả bốn dùng enqueueUniquePeriodicWork(…, ExistingPeriodicWorkPolicy.KEEP, …) ⇒ mở app nhiều lần không tạo job trùng; job cũ được giữ nguyên (kể cả chu kỳ đã trôi qua).

1.2. WorkManager + Hilt

Worker cần được tiêm dependency (@HiltWorker + @AssistedInject), nên WorkManager không được tự khởi tạo. Manifest tắt auto-init: 

<!-- AndroidManifest.xml -->
<provider android:name="androidx.startup.InitializationProvider"
          android:authorities="${applicationId}.androidx-startup"
          android:exported="false"
          tools:node="merge">
    <meta-data android:name="androidx.work.WorkManagerInitializer"
               android:value="androidx.startup"
               tools:node="remove" />
</provider>

Thay vào đó, Application cung cấp cấu hình qua Configuration.Provider:

@HiltAndroidApp
class HiltApplication : Application(), Configuration.Provider {
    @Inject lateinit var workerFactory: HiltWorkerFactory

    override val workManagerConfiguration: Configuration
        get() = Configuration.Builder()
            .setWorkerFactory(workerFactory)                 // ⭐ cho phép tiêm vào worker
            .setMinimumLoggingLevel(android.util.Log.INFO)
            .build()
}

2. Chi tiết từng worker

2.1. HealthSyncWorker — đồng bộ dữ liệu sức khỏe

fun schedule(workManager: WorkManager) {
    val constraints = Constraints.Builder()
        .setRequiredNetworkType(NetworkType.NOT_REQUIRED)   // Health Connect là offline
        .setRequiresBatteryNotLow(true)
        .setRequiresDeviceIdle(false)                   // không cần idle để dữ liệu cập nhật thường xuyên hơn chút
        .build()

    val syncRequest = PeriodicWorkRequestBuilder<HealthSyncWorker>(6, TimeUnit.HOURS)
        .setConstraints(constraints)
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.MINUTES)
        .addTag("health_sync")
        .build()

    workManager.enqueueUniquePeriodicWork(WORK_NAME, ExistingPeriodicWorkPolicy.KEEP, syncRequest)
}

Việc thật nằm ở repository — xem HealthDataRepositoryImpl.syncHealthData():

  1. Đọc snapshot Health Connect (null nếu thiếu quyền / chưa cài).
  2. Đọc số bước từ cảm biến của máy + giờ ngủ ước lượng.
  3. Trộn theo quy tắc ưu tiên nguồn.
  4. Nếu không có dữ liệu thật ⇒ return sớm, không ghi hàng toàn số 0 (sẽ làm nhiễu phân tích của AI).
  5. Gộp vào hàng của hôm nay (upsertToday).
  6. Dọn dữ liệu cũ hơn 30 ngày.
  7. Vẽ lại widget.

Kết quả trả về có phân biệt thật/giả:

override suspend fun doWork(): Result {
    return try {
        val syncResult = healthDataRepository.syncHealthData()
        // … log …
        if (syncResult.isSuccess) Result.success()
        // Đồng bộ thất bại THẬT → trả retry để WorkManager dùng backoff đã đặt,
        // thay vì luôn "thành công" khiến backoff không bao giờ chạy.
        else retryOrFail()
    } catch (e: CancellationException) {
        throw e         // WorkManager dừng worker = huỷ coroutine → ném tiếp
    } catch (e: Exception) {
        retryOrFail()
    }
}

/** Thử lại tối đa MAX_ATTEMPTS (3) lần rồi báo thất bại hẳn */
private fun retryOrFail(): Result =
    if (runAttemptCount < MAX_ATTEMPTS) Result.retry() else Result.failure()
Một chi tiết nhỏ nhưng đúng đắn

Trước đây worker luôn trả success dù đồng bộ lỗi ⇒ BackoffPolicy.EXPONENTIAL không bao giờ chạy. Nay phân biệt rõ ba trạng thái: success (xong, kể cả khi không có gì để đồng bộ), retry (lỗi tạm thời), failure (đã thử 3 lần).

2.2. SyncWorker — đẩy nhật ký lên Firestore

override suspend fun doWork(): Result {
    val userId = authRepository.currentUserId
    if (userId == null) {
        // Chế độ khách: bỏ qua và trả success — job vẫn chạy lại theo chu kỳ 6 giờ
        return Result.success()
    }

    return try {
        val cloudSync = settingsRepository.getCloudSync()
        val logsToUpload = CloudSyncPolicy.logsToUpload(
            logs = habitRepository.getUnsyncedHabitLogs(),
            settings = cloudSync
        )

        if (logsToUpload.isEmpty()) return Result.success()   // chưa bật đồng bộ / không có log nào hợp lệ

        logsToUpload.forEach { log ->
            firestoreSyncDataSource.uploadHabitLog(userId, log)
                .onSuccess { habitRepository.markHabitLogSynced(log.id) }
                .onFailure { throw it }               // một log lỗi → cả lần chạy coi là lỗi để retry
        }

        Result.success()
    } catch (e: CancellationException) {
        throw e
    } catch (e: Exception) {
        if (runAttemptCount < 3) Result.retry() else Result.failure()
    }
}

2.3. ReminderWorker — nhắc nhở hàng ngày

override suspend fun doWork(): Result {
    // Kênh đã được tạo lúc app khởi động (HiltApplication.onCreate); gọi lại cho chắc trong
    // trường hợp app chỉ chạy nền. Hàm này idempotent nên KHÔNG tạo kênh trùng.
    ReminderNotifications.ensureChannel(context)
    showNotification()
    return Result.success()
}

private fun showNotification() {
    val notification = NotificationCompat.Builder(context, ReminderNotifications.CHANNEL_ID)
        .setSmallIcon(android.R.drawable.ic_dialog_info)
        .setContentTitle(context.getString(R.string.notification_title))
        .setContentText(context.getString(R.string.notification_text))
        .setPriority(NotificationCompat.PRIORITY_DEFAULT)
        .setAutoCancel(true)
        .build()
    try {
        NotificationManagerCompat.from(context).notify(NOTIF_ID, notification)
    } catch (_: SecurityException) {
        // POST_NOTIFICATIONS chưa được cấp — bỏ qua, KHÔNG crash
    }
}

Ràng buộc duy nhất: setRequiresBatteryNotLow(true). Chu kỳ 24 giờ, KEEP.

2.4. SleepTrackingWorker — lấy mẫu giấc ngủ

Worker này khác ba worker kia một điểm quan trọng: nó nghe cảm biến. Nghe liên tục sẽ tốn pin, nên nó chỉ nghe trong vài giây rồi gỡ listener — đó là lý do chạy thưa 15 phút/lần vẫn không cần foreground service và không tốn pin suốt đêm. 

override suspend fun doWork(): Result {
    return try {
        val minutes = sleepTrackerRepository.sampleAndStore()
        android.util.Log.d(TAG, "Lấy mẫu giấc ngủ xong: $minutes phút cho đêm đang xét")
        Result.success()
    } catch (e: CancellationException) {
        throw e
    } catch (e: Exception) {
        if (runAttemptCount < 3) Result.retry() else Result.failure()
    }
}

val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.NOT_REQUIRED)   // đọc cảm biến là hoàn toàn offline
    .setRequiresBatteryNotLow(true)                   // không đánh thức máy khi pin yếu
    .build()

PeriodicWorkRequestBuilder<SleepTrackingWorker>(15, TimeUnit.MINUTES)
    .setConstraints(constraints)
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 5, TimeUnit.MINUTES)
    .addTag("sleep_tracking")
    .build()

SleepTrackerRepositoryImpl.sampleAndStore() được viết để không bao giờ ném: máy không có cảm biến gia tốc (hoặc cảm biến không trả về gì) thì chỉ trả số đã lưu. Cùng nguyên tắc với StepCounterRepositoryImpl.readTodaySteps().

3. Quy ước chung của ba worker "có thể lỗi"

Ba worker (HealthSync, Sync, SleepTracking) theo cùng một khuôn ba nhánh:

NhánhTrả vềVì sao
Thành công, hoặc "không có gì để làm"Result.success()"Không có gì để đồng bộ" không phải lỗi — retry sẽ vô ích
CancellationExceptionthrow tiếpWorkManager dừng worker = huỷ coroutine. Biến nó thành "retry/failure" sẽ che mất tín hiệu huỷ và coroutine không kết thúc đúng
Exception khácretry nếu runAttemptCount < 3, ngược lại failureDùng backoff đã đặt, rồi chịu thua thay vì thử mãi
Vì sao phải rethrow CancellationException

Nếu bắt nó thành Result.retry(), mỗi lần người dùng tắt mạng / hệ thống dừng job sẽ bị ghi nhận là "lỗi cần thử lại", làm backoff tăng vô ích. Tệ hơn, coroutine bị huỷ nhưng khối mã vẫn chạy tiếp sau điểm chờ. Quy ước này được áp dụng ở 14 chỗ catch (e: Exception) trong hàm suspend/worker, và 18 chỗ runCatching đổi sang runCatchingCancellable.

6. Luồng xin quyền trong app

Nguyên tắc chung: trạng thái quyền luôn được đọc lại từ hệ thống (nguồn đúng duy nhất), không tin vào tham số granted của launcher. Nhờ vậy cả trường hợp người dùng bật quyền trong Settings rồi quay lại app cũng đúng.

6.2. Đếm bước chân — và "cái bẫy thẻ không bao giờ hiện"

Nghịch lý tự chặn

Từ Android 10, cảm biến bước chân bị ẩn với app chưa có ACTIVITY_RECOGNITION: getDefaultSensor(TYPE_STEP_COUNTER) trả null. Nếu isAvailable chỉ dựa vào đó thì nó luôn false trước khi cấp quyền ⇒ thẻ xin quyền không bao giờ hiện ⇒ người dùng không có cách nào cấp quyền. Thế bế tắc "muốn cấp quyền phải thấy thẻ, muốn thấy thẻ phải có quyền". 

override val isAvailable: Boolean
    get() = stepCounterSensor != null ||
        context.packageManager.hasSystemFeature(PackageManager.FEATURE_SENSOR_STEP_COUNTER)
        // ⭐ cờ khả năng phần cứng KHÔNG phụ thuộc quyền

Quy tắc hiện thẻ và xử lý kết quả:

// HomeUiState — máy CÓ cảm biến nhưng CHƯA cấp quyền → hiện thẻ

Thẻ còn có nút phụ "Không thấy hộp thoại? Mở cài đặt quyền" cho trường hợp Android không hiện hộp thoại nữa (người dùng đã từ chối vĩnh viễn).

6.3. Nhận thông báo — ba trường hợp phải phân biệt

Việc suy ra trạng thái được viết thành hàm thuần để ba lối vào của thẻ đều khoá được bằng test:

fun from(sdkInt: Int, postNotificationsPermissionGranted: Boolean, appNotificationsEnabled: Boolean): NotificationPermissionStatus {
    val requiresRuntimePermission = sdkInt >= ANDROID_13_API
    // Android ≤ 12 không có quyền runtime → coi như đã có, chỉ còn công tắc cấp app
    val permissionGranted = !requiresRuntimePermission || postNotificationsPermissionGranted

    return NotificationPermissionStatus(
        notificationsEnabled = permissionGranted && appNotificationsEnabled,
        canRequestPermission = requiresRuntimePermission && !permissionGranted
    )
}

6.4. Quyền thông báo cũng ảnh hưởng lúc khởi động

HiltApplication.onCreate() gọi ReminderNotifications.ensureChannel(this). Trên Android 8+, app chưa có kênh nào thì trạng thái thông báo là "chưa xác định" và areNotificationsEnabled() trả kết quả khác nhau tuỳ bản Android/OEM ⇒ hành vi thẻ thay đổi theo máy. Tạo kênh ngay lúc khởi động (thay vì đợi ReminderWorker chạy — tối đa 24 giờ) làm hành vi giống nhau trên mọi phiên bản Android ngay từ lần mở app đầu tiên.

7. Health Connect rationale — đường vào bắt buộc phải có

Health Connect yêu cầu app cung cấp màn hình giải thích quyền riêng tư, và nó gọi app qua một intent. App phải xử lý hai hành động:

8. Bảng "việc gì chạy khi nào"

MỞ APP (lần đầu tiên)
  HiltApplication.onCreate
      └─ ReminderNotifications.ensureChannel            → kênh thông báo có ngay
  MainActivity.onCreate
      ├─ HealthSyncWorker.schedule    (6 giờ,  KEEP)
      ├─ SyncWorker.schedule          (6 giờ,  KEEP)
      ├─ ReminderWorker.schedule      (24 giờ, KEEP)
      ├─ SleepTrackingWorker.schedule (15 phút, KEEP)
      └─ Room mở DB lần đầu (SQLCipher + Keystore)

APP ĐANG MỞ / Ở NỀN TRONG TÁC VỤ
  HomeViewModel còn sống
      └─ listener cảm biến bước chân VẪN CHẠY  → số bước đếm tiếp

APP ĐÓNG HẲN (vuốt khỏi tác vụ)
  └─ listener bước chân DỪNG (phiên kết thúc)

LUÔN CHẠY DÙ APP ĐÓNG (WorkManager)
  ├─ mỗi 15 phút : SleepTrackingWorker   → nghe cảm biến 3 giây → cộng dồn giấc ngủ
  ├─ mỗi 6 giờ   : HealthSyncWorker      → gộp dữ liệu sức khỏe hôm nay + vẽ lại widget
  ├─ mỗi 6 giờ   : SyncWorker            → đẩy log lên Firestore (nếu đã bật đồng bộ)
  └─ mỗi 24 giờ  : ReminderWorker        → gửi thông báo nhắc nhở

KHI MÀN HOME HIỆN LẠI
  HomeViewModel.refreshSystemPermissions()
      ├─ kiểm tra lại quyền Health Connect
      ├─ kiểm tra lại trạng thái quyền thông báo
      ├─ đọc lại trạng thái cảm biến bước chân
      ├─ đọc lại giờ ngủ ước lượng
      └─ đọc lại nhịp tim GHI TRONG NGÀY   → đo xong quay về là thấy ngay

KHI MÀN PHÂN TÍCH HIỆN LẠI
  InsightsViewModel.refresh()
      └─ đọc lại chi tiết pha giấc ngủ (Health Connect không có Flow)

KHI APP GHI DỮ LIỆU SỨC KHỎE (đồng bộ xong / vừa đo nhịp tim)
  HealthWidget().updateAll(context)        → widget hiện số mới ngay (không chờ 30 phút)

9. Những điều đã ghi nhận nhưng chưa dọn

Hai quyền thừa trong manifest
  • SCHEDULE_EXACT_ALARM — không được dùng ở đâu: dự án không có AlarmManager hay setExact*() nào. Thẻ nhắc nhở dùng ReminderWorker (WorkManager), không dùng báo thức chính xác.
  • RECEIVE_BOOT_COMPLETED — trùng khai báo của thư viện work-runtime (WorkManager tự thêm khi cần để lên lịch lại sau khi khởi động).

Cả hai không ảnh hưởng build hay hành vi của app. Dọn bằng cách xoá hai dòng trong AndroidManifest.xml.

Widget vẽ lại theo 30 phút — vì sao không nhanh hơn

updatePeriodMillis của AppWidget có mức tối thiểu do hệ thống áp đặt là 30 phút. App bù lại bằng cách chủ động gọi updateAll() mỗi khi dữ liệu sức khỏe đổi — nên trong thực tế widget cập nhật ngay sau khi đồng bộ hoặc sau khi đo nhịp tim.

Phần cần máy thật/emulator để kiểm thử
  • CameraX và PreviewView (chụp ảnh, bind lifecycle) — không chạy được trên JVM.
  • Cảm biến đếm bước và cảm biến ánh sáng/gia tốc — emulator không có; muốn thử Health Connect thì phải bơm dữ liệu bằng Health Connect Toolbox (chỉ có trên emulator with Google Play).
  • Thông báo và Workspace scheduling thực tế — xem ở WorkManager Inspector trong Android Studio.
