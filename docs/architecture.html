Chương 2

Kiến trúc & luồng dữ liệu

HealthMate theo Clean Architecture 3 lớp kết hợp MVVM. Trang này mô tả luật phụ thuộc, vai trò từng lớp, cách Dagger Hilt lắp ráp hệ thống, và luồng dữ liệu từ phần cứng tới giao diện.

1. Luật phụ thuộc — điều quan trọng nhất

Toàn bộ kiến trúc quy về một luật: phụ thuộc chỉ được trỏ vào trong. Lớp domain ở giữa là trung tâm, và nó không biết gì về Android, Room, Firebase hay HTTP.

                    │  (biết domain + Android)  │
                    └───────────┬───────────────┘

    ┌───────────────────────────┴───────────────────────────┐
    │                       DOMAIN                          │
    │   model/  ·  repository/ (interface)  ·  usecase/      │

Vì sao luật này đáng giá

Vì domain chỉ phụ thuộc java.time + toán thuần Kotlin, nên mọi thuật toán của app test được trên JVM không cần emulator: đếm bước chân, suy luận giấc ngủ, phân tích PPG, chấm điểm sinh lực, sinh gợi ý, làm sạch kết quả AI. Đó là lý do 455 unit test chạy được trong vài giây.

2.1. Mẫu ViewModel thống nhất

Mọi ViewModel đều theo cùng một khuôn, nên đọc màn nào cũng đoán được cấu trúc màn khác:

@HiltViewModel
class HomeViewModel @Inject constructor(
    private val getTodayHabitsUseCase: GetTodayHabitsUseCase,
    private val healthDataRepository: HealthDataRepository,
    /* … các repository/use case khác được tiêm vào … */
) : ViewModel() {

    // 1. Một MutableStateFlow riêng tư + một StateFlow công khai (chỉ đọc)
    private val _uiState = MutableStateFlow(HomeUiState())
    val uiState: StateFlow<HomeUiState> = _uiState.asStateFlow()

    init {
        observeHabits()        // Flow từ Room → tự cập nhật khi DB đổi
        loadHealthConnect(showLoading = true)
        /* … */
    }

    private fun observeHabits() {
        combine(getTodayHabitsUseCase(), habitRepository.getHabitLogsForPeriod(0)) { habits, todayLogs ->
            /* … biến đổi thành danh sách hiển thị … */
        }
            .onStart { _uiState.update { it.copy(isLoading = true) } }
            .catch { e -> _uiState.update { it.copy(error = e.message, isLoading = false) } }
            .onEach { habits -> _uiState.update { it.copy(habits = habits, isLoading = false) } }
            .launchIn(viewModelScope)
    }
}

Điểm đáng chú ý trong khuôn này:

  • State bất biến (data class …UiState): UI chỉ vẽ theo state, không giữ state riêng.
  • State dẫn xuất nằm ngay trong UiState dưới dạng thuộc tính get() — ví dụ quy tắc chọn nguồn của thẻ tóm tắt sức khỏe (theo switch ở Trang chủ):
// HomeUiState — quy tắc hiển thị nằm CÙNG chỗ với dữ liệu nên test được.
// Nguồn CHÍNH do switch "Dùng dữ liệu Health Connect" quyết định:
//   BẬT → Health Connect (healthData); TẮT (mặc định) → bản chụp đã lưu trong app (storedHealthData).
// Nguồn chính KHÔNG có số thì dự phòng bằng cảm biến tự đo của máy.
val displaySteps: Long

    get() = if (healthConnectData.enabled) healthData.steps else storedHealthData.steps

val displaySleepHours: Double
    get() = primarySleepHours.takeIf { it > 0.0 } ?: sensorSleepHours
private val primarySleepHours: Double
    get() = if (healthConnectData.enabled) healthData.sleepHours else storedHealthData.sleepHours

val displayHeartRate: Double
    get() = primaryHeartRate.takeIf { it > 0.0 } ?: recordedHeartRate
private val primaryHeartRate: Double
    get() = if (healthConnectData.enabled) healthData.heartRate else storedHealthData.heartRate
  • Sự kiện dùng một lần (toast, mở hộp thoại) không dùng Channel mà là trường nullable + hàm "đã xử lý" — ví dụ HabitsUiState.showLogSuccessFor kèm onLogSuccessShown(). Nhờ vậy ghi nhận cùng một thói quen nhiều lần vẫn kích hoạt phản hồi mỗi lần.

File này dễ gây lỗi khó tìm nhất nếu làm sai thứ tự. Trình tự thật trong provideAppDatabase():

  1. System.loadLibrary("sqlcipher") — sqlcipher-android không tự nạp native lib; thiếu bước này là crash.
  2. Lấy passphrase từ DatabasePassphraseProvider (sinh mới hoặc đọc lại từ Keystore).
  3. Nếu passphrase vừa mới sinh ⇒ gọi LegacyDatabaseKeyMigration để rekey DB của bản cũ thay vì mất dữ liệu.
  4. Room.databaseBuilder(…).openHelperFactory(SupportOpenHelperFactory(passphrase.bytes)) và chỉ cộng thêm .addMigrations(*DatabaseMigrations.ALL) — không có fallbackToDestructiveMigration().

6.1. HiltApplication

Hai việc:

  • Khởi tạo Hilt (@HiltAndroidApp) và cung cấp HiltWorkerFactory để WorkManager tiêm được dependency vào worker.
  • Tạo kênh thông báo ngay lúc khởi động (ReminderNotifications.ensureChannel). Lý do rất cụ thể: trên Android 8+, app chưa có kênh nào thì trạng thái thông báo là "chưa xác định" và areNotificationsEnabled() trả kết quả khác nhau tuỳ OEM — làm thẻ "Bật nhắc nhở hàng ngày" hành xử không nhất quán. Tạo kênh ở đây (thay vì đợi worker chạy, tối đa 24 giờ) khiến hành vi giống nhau trên mọi bản Android ngay từ lần mở đầu tiên.

6.2. MainActivity

  1. Gọi schedule() của 4 worker (HealthSyncWorker, SyncWorker, ReminderWorker, SleepTrackingWorker). Dùng KEEP nên mở app nhiều lần không tạo job trùng.
  2. Kiểm tra intent có phải yêu cầu hiển thị rationale của Health Connect không (ACTION_SHOW_PERMISSIONS_RATIONALE hoặc ACTION_VIEW_PERMISSION_USAGE). Nếu đúng ⇒ hiện thẳng PrivacyPolicyScreen, không đi qua cổng đăng nhập — vì Health Connect sẽ từ chối duyệt nếu thấy app hiện màn Đăng nhập.
  3. Ngược lại ⇒ AppNavigation().

9. Quy ước code xuyên suốt

Bốn quy ước được áp dụng nhất quán ở mọi file; biết chúng thì đọc code không bị "bất ngờ".

9.1. Không bao giờ nuốt CancellationException

kotlin.runCatching bắt mọi Throwable, kể cả CancellationException. Trong hàm suspend, điều đó biến việc huỷ coroutine (rời màn hình, viewModelScope bị huỷ, WorkManager dừng worker) thành "lỗi nghiệp vụ": người dùng thấy thông báo lỗi trong khi thao tác chỉ bị huỷ, và coroutine không kết thúc đúng.

Dự án có hai biện pháp:

// util/RunCatchingCancellable.kt — dùng thay runCatching ở MỌI chỗ bọc suspend/I-O
inline fun <T> runCatchingCancellable(block: () -> T): Result<T> = try {
    Result.success(block())
} catch (e: CancellationException) {
    throw e          // ném tiếp, KHÔNG biến thành Result.failure
} catch (e: Throwable) {
    Result.failure(e)
}
// Với try/catch viết tay (đặc biệt trong HealthConnectDataSourceImpl):
try {
    val response = client.aggregate(request)
    response[StepsRecord.COUNT_TOTAL] ?: 0L
} catch (e: CancellationException) {
    throw e          // ⚠ phải đứng TRƯỚC catch (e: Exception)
} catch (e: Exception) {
    0L               // lỗi thật thì coi như "chưa có dữ liệu"
}

Có 14 chỗ catch (e: Exception) trong hàm suspend/worker được sửa theo quy ước này, và 18 chỗ runCatching đổi sang runCatchingCancellable.

9.3. Dữ liệu "hôm nay" luôn căn theo 00:00 của múi giờ thiết bị

Mọi mốc "hôm nay" dùng cùng một công thức (xem HealthDataRepositoryImpl.startOfToday(), HabitRepositoryImpl.startOfDayEpochMillis()). Điều này khiến chỉ số tự "đọc lại từ đầu ngày": 

private fun startOfToday(): Long = LocalDate.now()
    .atStartOfDay(ZoneId.systemDefault())
    .toInstant()
    .toEpochMilli()

Nhờ vậy sang ngày mới, ô "Tim" hiện -- bpm thay vì số của hôm qua, và tiến độ thói quen không bị "về 0 mỗi lần mở lại màn hình" (lỗi cũ: mốc được tính là now - daysBack).

9.4. Đọc lịch sử theo mốc thời gian, không theo số hàng

health_data_history có thể có nhiều hàng trong cùng một ngày. Cắt theo số hàng (LIMIT 30) khiến luật "3 ngày liên tiếp" của Rule Engine âm thầm không chạy. Vì vậy API chính là getHealthHistorySince(fromTs); tầng dùng tự gom theo ngày.
